Interpretation:

- Timestamps are integer Unix epoch milliseconds; `1672617600000` decodes to `2023-01-02 00:00:00 UTC`. They are all exact 5-minute UTC boundaries, seconds are zero, rows are sorted ascending, and there are no duplicate timestamps or duplicate rows.

- There are 106 timestamp gaps larger than 5 minutes: 98 regular weekend gaps (32 × 26h05 and 66 × 27h05), plus 8 holiday/early-close gaps listed above (Easter, Thanksgiving, Christmas/New Year, and two short holiday gaps).
- 33,815 bars are flat (`open == high == low == close`), 19.25% of the file; 27,338 of those are Sundays. The feed pads closed periods with flat bars (first non-flat bar is `2023-01-02 23:00`), so the raw timestamp gaps understate the real market closure. The simulator sees these padded bars; it does not filter them.
- This padding affects the strategy's previous-day levels: 102 of 291 raw-data trades have a prior-day flat ratio above 50%, and 98 trades occur on Mondays. The raw real-data result below should therefore not be treated as a clean performance estimate.

## Range variants F/G/H on all data (2026-11-03)

### Scope and implementation

Added three fixed variants separate from A-E in `research/london_range_breakout.py`. The existing A-E implementation was not changed. This is simulator-only; no broker or order path is involved.

- F: range high/low from 00:00-07:00 UTC; entry window 07:00-11:00 UTC. Enter at the next candle open after a 5-minute close beyond the range. Stop is the opposite side of the range. Target is 2R. Time exit is 11:00 UTC. One trade per day.
- G: range high/low from 07:00-08:00 UTC; entry window 08:00-11:00 UTC. Same entry, stop, target, and exit rules as F.
- H: uses the F range. If a 5-minute candle closes beyond the range and a close returns inside within the next 3 candles, enter against the break at the next open. Stop is the extreme of the failed break (highest high for a failed upside break, lowest low for a failed downside break) across the breakout and re-entry candles. Target is the range midpoint. Time exit is 11:00 UTC. One trade per day.

No parameters were tuned. No variants were combined. Costs are applied as `net_r = gross_r - cost_r`; trade counts are therefore identical across the three cost assumptions.

## Variants I, J, K

### Scope and fixed rules

- Variants I/J/K are separate from A-H. A-H were not changed.
- No parameter tuning, no parameter search, and no variant combinations.
- Simulator only; no broker, order, or live-trading path.
- Variant I uses the cleaned 5-minute XAUUSD bid data for all years 2020-2026.
- Variants J/K use daily gold data downloaded from 2010 so SMA(110)/SMA(250) have warmup history.
- I: long when close < lower Bollinger(20,2) and RSI(14) < 30; short when close > upper band and RSI(14) > 70. Entry at next 5-minute open. Exit on intrabar SMA(20) touch. Stop = 2 x ATR(14) measured at the signal bar. Time exit after 48 bars, counting the entry bar as bar 1. One position at a time. Stop is checked before SMA touch on the same bar. Bollinger uses population standard deviation (`ddof=0`). Costs are deducted as `net_r = gross_r - cost_r`.
- J: long after a closed bullish daily candle with close > SMA(110) and ADX(14) >= 20; short after a closed bearish candle with close < SMA(110) and ADX(14) >= 20. Entry at next daily open. Exit at next daily open when the entry condition no longer holds; if the opposite condition holds on that close, the position flips. One position at a time. No costs were specified, so J returns are gross simple price returns in percent, compounded for the yearly total.
- K: long when the prior daily close > SMA(250), otherwise cash; position is applied to the next daily return. No costs were specified. Entries count cash-to-long transitions. Buy-and-hold uses the same close-to-close date range as the strategy.

## Phase 1 build: read-only data layer + market viewer

This phase adds the read-only data layer, one canonical market viewer, and the read-only MCP config. It does not change trading logic, `.env`, broker credentials, or existing strategy algorithms.

### Scope

Only these files change:

- `opencode.json` (new)
- `market_data.py` (new)
- `market_viewer.py` (new)
- `dashboard.py` (compatibility wrapper)
- `tests/test_market_data.py` (new)
- `tests/test_market_viewer.py` (new)
- `tests/test_opencode_config.py` (new)

Nothing in `trader/`, `intraday_bot/`, `.github/`, or `.env` has been modified.

### Market data layer design

New abstraction: `MarketDataProvider` Protocol in `market_data.py`. It defines only `name`, `list_symbols`, and `get_bars(symbol, start, end, timeframe)`.

Current implementations:

- `CsvMarketDataProvider`: scans `data/` and `intraday/` for OHLCV CSVs, normalizes timestamps to UTC, fills missing volume with zero, de-duplicates bars, and records `invalid_ohlc` counts in `frame.attrs` rather than silently repairing them.
- `AlpacaMarketDataProvider`: read-only bars provider around `StockHistoricalDataClient`. It has no order endpoints and never imports `TradingClient`.

Planned next step: route the existing strategy layer through `MarketDataProvider`, then switch between CSV and Alpaca using a single configuration flag.

### How switching will work

To keep the strategy core unchanged, the backtest and paper-trading entry points should accept a provider object rather than reading files or calling the broker themselves.

- Add a single factory function, e.g. `make_provider(kind, **kwargs)`, that reads a config field such as `--data-source` or `DATA_SOURCE` (values: `csv`, `alpaca-paper`).
- The strategy layer keeps using `get_bars(symbol, start, end, timeframe)`, and both providers return the same normalized `pd.DataFrame` (tz-aware index, `open`, `high`, `low`, `close`, `volume`).
- Strategy code should not branch on provider type; it only sees the returned frame.
- Alpaca creds are read from environment only, never written into settings.

Because both providers produce the same shape, no per-strategy edits are required. A future change can add parquet, databases, etc. without touching algorithms.

### Unified read-only viewer

Canonical viewer: `market_viewer.py`. It replaces the two older dashboards with one local page that can serve or write static HTML.

It shows:
- multi-asset candlestick cards
- OHLC integrity summary per asset
- paper swing and intraday sleeve metrics
- read-only / localhost-only footer

Run:
```text
python -m market_viewer --serve --open
```

Compatibility wrapper: `dashboard.py` delegates to `market_viewer.py`, so both `streamlit run dashboard.py` and `python dashboard.py` still work.

### opencode MCP configuration

`opencode.json` adds only the read-only `fin-data` MCP server. It is local, read-only, and has no credentials in the file.

### Security checks

- `opencode.json` contains no keys, secrets, tokens, bearer credentials, or broker references.
- `market_data.py` and `market_viewer.py` never import `TradingClient`, `submit_order`, `close_position`, or `cancel_order`.
- The viewer reads local CSVs and journals only; it cannot place, cancel, or close orders.
- The viewer server binds to `127.0.0.1` and exposes GET-only endpoints, with 405 for POST/PUT/DELETE.
- Old `trader/`, `intraday_bot/`, and `.env` stay untouched.
